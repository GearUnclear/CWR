2. AITEST review: do the new tests fail if render path state leaks into AI sight?
--------------------------------------------------------------------------------

Mostly yes. [aisight] passes on the merged build: 298 assertions in 5 cases, run from D:\ with
build/look-director-rwdi PoseidonTests.exe.

What the tests cover (tests/unit/engine/Poseidon/World/test_fog_sight_link.cpp):
  - Case "ignores every render path state" runs the real call, SimulateFogSight(&land), on a real
    Landscape (a 64x64 valley at setFog 0.3) under an EngineDummy subclass that reports each state:
      post effects off, classic lighting, volFog off, fogQuality/fogSun/fogLights, every gate off with
      an interior view, another drawn medium, no drawn medium, tacticalZ 300, GEngine null.
    For each state it checks the AI medium's march fields and FogSightTransmittance with exact
    equality (==).
  - SimulateFogSight passes GEngine->GetLightingTuning() whole into ComputeFogMedium(in, t, true).
    Any leak placed in SimulateFogSight, ComputeFogMedium or FogSightTransmittance that reads one of
    those states changes a value, and the case fails. That includes the fixer's mutation,
    "if (!tuning.postEffects) SetFogSight(nullptr, nullptr)".
  - I could not re-run the mutation: it needs a source edit and a rebuild, and no log of the fixer's
    mutation run is on disk. Reading the code agrees with the fixer's claim.
  - SetDrawnFogMedium copies its argument, so the lambda's local "other" medium does not dangle.
  - FogSightMedium() now returns by value; a static_assert pins it.
  - The classic early return in UploadLitFrameConstants clears the drawn medium
    (EngineGL33_Lighting.cpp 796).

Gaps, where a leak would still pass every unit test:
  a) The call site is checked by string only. The contract finds "SimulateFogSight(GLOB_LAND)" in
     World::SimulateLandscape, after the sun, the weather and SetFog and before PerformAI. It does not
     check that the call is unconditional, and the render-state token check covers only the bodies of
     SimulateFogSight and WorldFogInputs. A guard such as "if (GEngine->LightingRemasterActive())
     SimulateFogSight(GLOB_LAND);" in WorldSetup.cpp would pass. AI would then keep a stale medium, or
     none.
  b) The consumer is checked by string only. In Target.cpp, EntityAI::CalcVisibility is checked only
     for FogSightActive() before the "vis *= FogSightTransmittance(from, to)" text. No unit test
     executes it. A render condition wrapped round the multiply would pass; only the in-game probe verb
     triAiSight would show it.
  c) Through the real step, case 1 does not vary exposure, saturation or sun. Case 4 covers them in the
     pure ComputeFogMedium only. A read of those knobs inside SimulateFogSight itself would slip.
  The cheap fix for (a) and (b): extend the token check to SimulateLandscape's body up to the call and to
  CalcVisibility's fog branch. Better, drive CalcVisibility in a unit test. None of these gaps blocks the
  look.
  Still open, not part of this change: the ground field is about 0.6 s late after island load, and AI's
  weather part is still the classic tactical fog (owner call).


3. Cost
-------

How I ran it: tests/rendering/captures/run-timing.ps1 from the look-director engine root against
dist/look-director-rwdi, junction RemasterUD-look-director-timing. Tests: critic_r4_artefacts/tests
crit4t_abel_a/b/c, crit4t_eden and crit4t_sinai, the 21 views of round2/cost.md. Each view was shot 2x
"tip" (remastered,photoLight=0,surfaces=0,volFog=0) and 2x overhaul, in the same build.

The machine was quiet:
  - before each of the 4 runs, tri slots read 0/4 and no PoseidonGame was running (0 s wait);
  - the GPU sampler logged 0 of 142 two-second samples with a foreign PoseidonGame;
  - round 3 also had 0 of 142, while round 4's run was contaminated, with 170 of 179 samples foreign.
Table: timing/cost_r5_table.txt (script timing/cost_r5.py). Raw data: timing/<part>-timing/.

GPU frame, overhaul minus tip, mean over the 21 views:
  r2 +1.40 ms   r3 +1.45 ms   r5 +1.52 ms   (r4 +1.94 ms, not quiet, disregard)
  median: r2 +1.47, r3 +1.61, r5 +1.50; mean ratio overhaul/tip: r2 1.152, r3 1.158, r5 1.158
  min-frame delta: r3 +1.58 ms, r5 +1.65 ms

Per view, versus round 3:
  - Most views are within +-0.3 ms.
  - Real growth is in the low-sun day views:
      dawn_valley +2.60 -> +3.07 ms (min-frame +3.22 -> +3.72; world pass +3.47), 34.4 ms in all
      sunrise_ridge +0.21 -> +0.68
      woods_pine2_evening +1.45 -> +1.78
    This fits the dawn fixer's per-column ring phase gain: 9 extra sky-table taps per froxel column
    in psFogInject, active by day with the sky table on.
  - town_night_rain shows +2.75 against r3's +1.61, but one overhaul sample spiked (frame 16.6 ms, min
    12.7). Its min-frame delta is +1.04 against r3's +1.71, so I see no regression from puddle option 4.
  - jeep_close_noon's +0.77 is low for the same reason, a spiked tip sample.
  - CPU frame time with the overhaul on: 15.80 ms against 15.48 in round 3 (the tip runs went
    14.25 -> 14.40). This is noise level; the particle rig light is one upload per frame.
The heaviest view is still dawn_valley, at 34.4 ms here, against 31.3 ms for the tip.
