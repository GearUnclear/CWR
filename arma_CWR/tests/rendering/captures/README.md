# Lighting captures: Classic | Remastered

A repeatable, scripted in-game photo run for the Remastered lighting work
(`engine/Poseidon/Graphics/Remaster/README.md`). Every view is shot twice with
the same camera, sim clock, date, weather and props, once with
`triSetLighting "classic"` and once with `triSetLighting "remastered"`, and the
GPU and CPU frame timings of each mode are logged next to the image.

These are photo generators, not regression tests: they assert nothing and live
outside `tests/integration/`, so a `tri test tests/integration` sweep never
picks them up. Run them explicitly.

## Preconditions

- A built game in `dist/x64-win-rwdi`, the stage dir of the `win-x64-clang-rwdi` preset (or pass `-GameDir`).
- `packages/RemasterUD`: the gitignored junction to the setup-prepared full
  Remaster shadow. From `arma_CWR`:
  `cmd /c mklink /J packages\RemasterUD <shadow>`, where `<shadow>` is the
  main checkout's `tmp\remaster-shadow-67` (the runner's `-ShadowDir` default).
  The Sinai test mounts the shadow's own `@LoBo` copy (`--mods-dir . --mod @LoBo`,
  the same as the `remaster_ud` Sinai tests), which carries the mod doctor repairs.
- `tri.exe`: `target\debug\tri.exe` of this tree, else of the main checkout
  (or pass `-Tri`).
- Python 3 with Pillow on `PATH` as `python` (or pass `-Python`).

## Running

From `arma_CWR` (PowerShell):

```powershell
powershell -NoProfile -File tests\rendering\captures\run-captures.ps1
# one island only:
powershell -NoProfile -File tests\rendering\captures\run-captures.ps1 -Tests tests/rendering/captures/eden_lighting.test.sqf
# rebuild pairs and tables from an earlier run, no game launched:
powershell -NoProfile -File tests\rendering\captures\run-captures.ps1 -CollectOnly -OutDir ..\tmp\captures\20261017-140000
```

The script runs `tri test --retries 1 -j1 --game-dir <GameDir>
--output-dir <out>\tri <tests>` through `tmp\tri-hidden-desktop.ps1`, a local
untracked wrapper (a private desktop, so no game window takes the focus; `-Visible`
runs tri directly instead and needs no wrapper). Afterwards it always calls
`tools\stop-owned-games.ps1 -DataDir <arma_CWR>\packages\RemasterUD`:
tri starts every game with `-C <that junction path>`, so only this worktree's
games match (never a global `Stop-Process`). Paths in the tri command line must
not contain spaces (the wrapper passes it through `cmd /c`).

## How a pair is shot

Per view (`capBegin`) the test sets the camera, date, weather and view
distance, spawns the props, and lets 150 frames pass. Then, for Classic and
again for Remastered:

1. `capMode`:
   - `triPinObjectDetail capDetail` (1, the finest detail the quality setting
     allows): the same object detail for both shots. Left adaptive,
     `Scene::AdjustComplexity` picks the detail from the frame time and
     refuses to refine for five seconds after it last coarsened, so a shot
     soon after a camera jump drew a fraction of the scene. On sunrise_ridge
     the adaptive detail drew 1,063 objects for about 3 s after the jump and
     7,680 once it refined; the perf research track's replay of this rig
     logged 1,465 draw calls for the Classic shot there against about 9,500
     later. Whether a shot falls inside that window depends on the frame
     time, so it varied with the machine's load from run to run.
   - `triSetLighting "<mode>"`: the lighting model with every tuning knob back
     at its shipped default, so knobs a variant set never reach the next one
     (Remastered also turns the shadow maps on, Classic turns them off, as the
     Options row does).
   - `triSettleScene capSettleArgs` (`[300, 30, 2]`): frames until the view
     has finished loading. Settled = the last 30 frames drew within 2% of the
     same number of draw calls, at one LOD width, with no terrain horizon map
     build in flight. The per-frame texture upload budget is lifted on these
     frames, so textures in view are not held back at a coarser mip. It
     answers `OK:<frames>`,
     or `UNSETTLED:<frames>` after 300 (logged, and listed by `make_pairs.py`;
     the shot is still taken).
   - `triGpuTimes false` / `true` and `triPerfReset`, which restart the GPU
     and CPU averages.
2. `triSimFrames 90`: the timers settle. GPU results trail the frame by a few
   frames and are an exponential average with weight 0.1, so 90 frames leave
   well under 1% of anything earlier in them.
3. `capReadTimers`: `triGpuTimes true` (the summary string, read while timing
   is still on; `false` would answer "gpu: timing off") and `triPerfStats 0`.
4. `capPin`: the same `setDate`, `triCheatWeather` + `setOvercast` / `setFog`
   / `setRain 0`, view distance, prop positions, `triSetView` and
   `triSetSimTime` as the other mode. Re-pinning the sim clock puts water,
   sky and the remastered cloud-shadow drift (keyed on `Glob.time`) back where
   they were. It moves `time` back a few seconds for the second shot; nothing
   in these static scenes depends on that.
5. `triSimFrames 3`, then `triScreenshot "<view>__<mode>"` and `capRecord`.

Settings shared by every shot: 960x640 windowed (`--display-mode windowed
--width 960 --height 640`), `triSetMsaa 4`, `triSetRenderScale 1.5`, and
`triCaptureAtPresent true`, so the image is the presented frame after the gamma
pass (the default `triScreenshot` reads the frame before gamma, darker than what
a player sees). The remastered exposure meter is a pure function of the sun
height (`LightRig.cpp`) and the classic eye accommodation is instant, so there
is no adaptation to wait for between the two modes. The pinned finest object
detail is what a fast machine settles on, and the frame timings are measured
on it, so on long views they come out higher than in older runs, which shot
whatever the adaptive detail had reached.

Street lamps: `setDate` (`capPinEnv`) now switches the auto street lamps for the
new time at once, as `skipTime` does (`World::SetDate`). Before, they kept their
old state until their next simulation tick (every 12 s), so a view whose date
crossed dusk or dawn could change lamps between or during its two shots. Once a
lamp has been lit its light slot stays, and any slot turns instancing off for
the whole scene (`SceneDraw.cpp`, Pass1), so later views draw several times more
calls for the same objects (sunrise_ridge: 2,797 draw calls with no slot, 11,172
with 12, both 7,680 objects). Compare `objects=` between shots, not `draws=`.

Framing uses the `tools/screenshots` rig: a cutscene camera exists only to hide
the HUD and give `camSetFov` a target, and `triSetView [east, up, north, dir]`
sets the exact eye point; the eye height comes from a ground probe (an invisible
`HeliHEmpty` at `[x, z, 0]`, read back with `getPosASL`), so no terrain height
is hard-coded. Props are placed relative to the view origin and heading
(`capSpawn`, `[forward, right]` in metres). A class that does not exist in the
merged config is skipped and logged (`event=skip_spawn`), a spawn that fails is
logged (`event=spawn_failed`), and the view is still shot. Every tri verb that
can answer `FAIL:` is called inside a helper and its answer logged, because a
top-level `FAIL:` result aborts the whole test.

Notes on the choices:

- **Acceptance stand-in.** The owner's `LightingLowSun.Demo` was on the `demo`
  world, which the Remaster shadow does not have. `lowsun_fp` rebuilds it on
  Abel. The Remaster's vanilla data ships no camouflage-net class (CONFIG.BIN,
  AddOns and DTA searched), so the net's candidate list is `LoBo_camnet`
  (@LoBo, `LoBofightpos.pbo`), then `CampEast`, then `Camp`: on Abel without
  mods it is the Soviet tent, on Sinai it is the real net.
- **Sun on Sinai.** @LoBo's `CfgWorlds >> sinai >> latitude = 29.39`, but the
  engine's convention is the opposite sign (`DefaultWorld` -40 is 40 deg north,
  `WorldInit.cpp`, `Lights.cpp`), so the engine puts Sinai at 29.4 deg south and
  the noon sun in the north. The Sinai times and headings follow what the
  engine does.
- **How the spots were found.** `PoseidonTools terrain objects <wrp>` (columns
  `[east, elevation, north]`) for trees, lamps and towns, and the heightmap
  from `PoseidonTools terrain render`, whose colour ramp
  (`Asset/Probes/AssetPreview.cpp` `PreviewTerrain`) inverts back to metres
  (checked against road objects: median 1.4 m above the decoded ground on Abel,
  0.9 m on Sinai). Each spot was then scored for slope, nearby objects, the
  horizon angle along the sun's azimuth and what lies along the view heading.
  `sunplan.py --scan <y> <m> <d> [lat]` lists a day's sun path for re-planning.

## Feature A/B (features_ab)

Every lighting feature of the integration plan has a switch, a key of the
registry in `engine/Poseidon/Graphics/Remaster/FeatureSwitches.hpp` (0 off,
1 on, all on by default), and a frame gate (`FeatureGates.hpp`).
`gen_features_ab.py` writes `features_ab.test.sqf`: for each feature its hero
view (the start view of its first row in plan section 7.3, `views.HERO`), shot
first with `triSetLighting "remastered,<its keys>=0"` (`<view>__off`) and then
with `"remastered"` (`<view>__on`). Both shots share the camera, date, weather,
props, sim clock and clouds (`triPinCloudDrift` holds the remastered cloud
shadows and the sky clouds, which otherwise move on every frame whatever the sim
clock says). `make_pairs.py` builds `<view>__pair.png` with the off shot left.

```powershell
python tests\rendering\captures\gen_features_ab.py          # after editing views.HERO
powershell -NoProfile -File tests\rendering\captures\run-captures.ps1 -GameDir dist/graphics-remaster-rwdi -DataJunction RemasterUD-gr-<step> -Tests tests/rendering/captures/features_ab.test.sqf
# gate item 5, off equals baseline: this build's off against the previous build's on
python tests\rendering\captures\banddiff.py <run new> <run previous> --label-a off --label-b on --md off-vs-baseline.md
# gate item 6, and the repeat noise where off and on draw the same frame
python tests\rendering\captures\banddiff.py --pairs <run> --md off-vs-on.md
```

The mode word `baseline` (every switch off, every knob at its default) is the
look of the graphics-remaster branch cut; `remastered` is every switch on.
`triFeatureState` answers every switch with its gate
(`<key>=<value>:<on|off>[@<scale>]:<reason>[:inert]`, `:inert` while nothing
reads the switch yet) and is logged with every shot as `feat=`.

## Timing

`run-timing.ps1` runs `timing_abel`, `timing_eden` and `timing_sinai` (the A0
baseline views, regenerate with `gen_timing.py`) with `gpu_sampler.ps1`
logging the GPU clock, P-state, load and every foreign PoseidonGame every 2 s,
then `summarize_timing.py` writes `timing.md` (median and minimum over the
rounds, the GPU clock per shot). Run it only on a quiet machine (`tri slots`:
no other holders), and compare a light view's milliseconds only at a matching
clock: the GPU picks its clock from the load.

## Log lines

Every helper writes `UDCAP;view=...;event=...` at INFO through `logInfo`, which
tri saves in the test's `game_stdout.log`. Events: `setup`, `begin` / `view`
(camera, date, weather, ground-probe and `triSetView` answers), `spawn`,
`skip_spawn`, `spawn_failed`, `mode` (the `triSetLighting` answer, the
`triPinObjectDetail` answer as `detail=`, the `triSettleScene` answer as
`settle=`, then the `triSceneStats` fields at the end of the wait), `shot` (one
per image: label, mode, lighting answer, `triCamView`, `triFps`, the shot
frame's `triSceneStats` fields `draws=` (GL draw calls), `objects=` (objects
with a visible LOD, before occlusion; the number to compare between the two
models, whose draw calls for the same objects can differ a little), `lights=`
(light slots: once a street lamp has been lit its slot stays, and any slot
turns instancing off for the whole scene, which multiplies the draw calls of
the same objects), `lod=` (Scene LOD width), `pin=` (0 = adaptive) and
`horizon=` (`off`, `pending` or `ready`), `feat=` (`triFeatureState`: every
feature switch and its frame gate), `triPerfStats` (its `calls=` is the timing
window's mean), and last the `triGpuTimes` summary), `clouds` (the
`triPinCloudDrift` answer of a generated test), `frame` (one per video frame),
`squads`, `tank`, `done`. The game log also carries a
`[tri] triSettleScene:` line per mode with the draw-call range of the last
window.
